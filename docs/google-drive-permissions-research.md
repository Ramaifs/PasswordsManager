# Доступ к Google Drive через разрешение пользователя

Проверено 2026-10-25 по официальной документации Google. Настройки аккаунта,
регистрация проекта, платежи и настоящий OAuth-вход в рамках исследования не выполнялись.

## Вывод

Да: приложение может показывать «Подключить Google Drive», затем официальное
окно выбора аккаунта и разрешения доступа. Google возвращает приложению access
token, который разрешает вызовы Drive API в пределах согласованных scopes.
Именно это называется OAuth consent. Пользователь не передаёт приложению пароль
Google и не создаёт собственный Google Cloud проект для каждого подключения.
Источник: [Google Identity Services: token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model).

При этом один проект и OAuth client ID всё равно регистрирует владелец приложения:
Google должен знать, какому приложению пользователь разрешает доступ. Для сайта
и Windows нужны отдельные OAuth client ID соответствующих типов. Это настройка
разработчика, а не обязательное действие каждого конечного пользователя.
Источники: [создание OAuth credentials](https://developers.google.com/workspace/guides/create-credentials),
[настройка Web client и origins](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

## Карта и billing

Официальная инструкция Google Workspace отделяет создание проекта от включения
billing и прямо обозначает последнее как необязательный шаг, зависящий от
используемых API и функций. Поэтому регистрация проекта сама по себе не равна
регистрации платного Google Cloud аккаунта или активации пробного кредита.
Источник: [Create a Google Cloud project](https://developers.google.com/workspace/guides/create-project).

Drive API указывает отсутствие дополнительной платы для стандартного использования.
Но утверждение «Drive API всегда полностью бесплатен при любой нагрузке» уже
некорректно: с 1 мая 2026 изменены квоты для новых проектов, а платное превышение
стандартных дневных порогов анонсировано на более поздний срок 2026 года с
предварительным уведомлением минимум за 90 дней. Включение Cloud Billing
потребуется для расширения квот в рамках объявленной модели.
Источники: [Drive API: Usage limits / Pricing](https://developers.google.com/workspace/drive/api/guides/limits),
[Workspace standardized model](https://developers.google.com/workspace/tools-safety).

Практический вывод из этих источников: для небольшого личного менеджера паролей
в стандартных квотах следует использовать проект без включения billing, а не
оформлять платную пробную подписку ради OAuth. Документация не устанавливает
требование банковской карты именно для пользовательского окна разрешений.
Однако это не проверка конкретного аккаунта: неизвестно, какой именно экран
запросил у пользователя Visa, и нельзя обещать отсутствие любых дополнительных
проверок аккаунта или ограничений организации.

## Подход для этого проекта

1. Владелец приложения открывает [создание проекта](https://console.cloud.google.com/projectcreate),
   создаёт проект и включает Drive API; Cloud Billing и платный trial не активирует.
   Путь проекта и необязательность billing описаны в
   [инструкции Workspace](https://developers.google.com/workspace/guides/create-project).
2. Настраивает OAuth consent и два клиента: Web application с точным origin
   сайта и Desktop app для Windows. Затем параметры приложения включаются
   в его конфигурацию; обычному пользователю остаются кнопка входа и согласие.
   [Создание credentials](https://developers.google.com/workspace/guides/create-credentials).
3. Приложение запрашивает узкий scope `drive.file`: доступ к созданным приложением
   файлам или файлам, которые пользователь явно предоставил приложению. Это не
   разрешение читать весь личный Drive.
   [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).
4. Если консоль всё же останавливает именно создание/включение Drive API требованием
   billing, нужно установить точный URL и текст этого экрана; не подменять consent
   извлечением cookies, чужим OAuth client ID или автоматизацией аккаунта.

Реальный вход, consent и сетевой обмен текущего менеджера требуют отдельной проверки
после регистрации OAuth-клиентов. Это исследование подтверждает официальный механизм,
а не успешную авторизацию существующей сборки.
